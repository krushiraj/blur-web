# Plan: Blur playable in the browser at up to 120 fps

Written 2026-10-16 from (a) the state of the port (see `PROGRESS.md`) and (b) research on browser/WebAssembly capabilities.
Items marked **[verify]** are assumptions that the first phase must confirm or kill. Nothing here is committed or published; the game data stays local.

## 0. Where we are / hardware

- Works: statically recompiled game (373k functions) runs natively, streams D3D9 to a WebGL2 page over WebSocket; front-end 3D scene at ~60 fps (378 draws/frame). Command generation alone sustains ~180 fps.
- Missing for "playable": menu/UI never appears (state unknown), black car paint, no audio, no movies (Bink), keyboard only, no saves, and it is **native + WebSocket, not yet a browser-only build**.
- Machine: Apple M4 Max (16 cores, 128 GB, 3024x1964 ProMotion). Hardware is not the limiter; the 8.33 ms/frame budget at 120 fps is a software problem (guest CPU time + GL call overhead + pacing).

## 1. How a professional would approach this (principles)

1. **Metrics before features.** Instrument per-frame time split (guest code / HLE / command encode / GL) and sim-time behaviour first; all later decisions follow the numbers.
2. **Keep the native build as the reference harness.** Fix gameplay and rendering bugs natively (seconds to rebuild, real debuggers, oracle diff), then port the *same* source to wasm. Never debug game logic and the wasm port at the same time.
3. **Vertical slice early.** Get "menu -> race -> finish" playable on the slow/simple path (single-thread, WebGL2, no polish), then optimise the measured hot spots.
4. **Platform layer boundary.** Win32/D3D9/audio/input/file HLE sits behind a small interface so the same code runs natively and in wasm.
5. **Regression safety.** Deterministic input replay + golden frame hashes + the existing oracle, run on every recompiler change.

## 2. Research findings that shape the design

| Topic | Finding | Consequence |
|---|---|---|
| Wasm tail calls | Shipped in Chrome 112, Firefox 121, Safari 18.2 (webassembly.org/features) | Our `MUSTTAIL` dispatch model maps to `return_call`; build with `-mtail-call`. |
| Memory | wasm32 can address 4 GB (`MAXIMUM_MEMORY=4GB`, opt-in). memory64: Chrome 133+, Firefox 134+, Safari not yet | Guest user space is ≤0x7ffe0000 (2 GB) -> **wasm32 with guest address == wasm address** (plain loads, no base add). Host heap/state sit above 2 GB. memory64 not needed. |
| Compile time | V8: Liftoff is tens of MB/s; TurboFan on large modules takes 30–60 s+; compiled code is ~5–7x module size; code cache only helps if the module fits | **A 170 MB-native-equivalent module is too big.** Must shrink to a hot set (Phase 4) and rely on code caching + tier-up. |
| Threads | Emscripten pthreads need SharedArrayBuffer + COOP/COEP | Avoid: our runtime already uses baton scheduling, so run all guest threads **cooperatively on one wasm thread**. |
| Blocking/async | Asyncify/JSPI exist, but our whole CPU state lives in the `Cpu` struct and guest stack | The run loop can simply **return to JS at any point (e.g. at Present) and resume next frame** — no Asyncify needed. |
| Rendering | WebGL2 is the safe path; WebGPU (command encoder/render bundles) is the higher-ceiling path | Start WebGL2 + state-dedup; keep renderer behind an interface so a WebGPU backend can replace it if GL overhead dominates. |
| File access | Dedicated workers get **synchronous** OPFS access handles | Guest `ReadFile` stays synchronous without Asyncify; user imports their own game folder once into OPFS. |
| Movies | Game uses `BIKi` (Bink 1); FFmpeg has Bink video/audio decoders | Phase 1: skip movies. Later: offline transcode to WebM/H.264 for WebCodecs, or libavcodec-bink in wasm. 2.6 GB of .bik. |
| Prior art | XenonRecomp / N64Recomp: static recomp + hand-written HLE; indirect calls via lookup table; per-title "patch" hooks | Same architecture as ours; their lessons: keep a hook mechanism for game-specific fixes (incl. frame-rate patches), build for incremental coverage. |

## 3. The 120 fps question (biggest unknown) **[verify]**

120 fps needs two independent things:
1. **Presentation rate**: Chrome's `requestAnimationFrame` follows the display (120 Hz on ProMotion). Make `Present` yield to rAF; render in a Worker with `OffscreenCanvas`.
2. **Simulation rate**: Blur (2010 console-era) very likely runs a fixed 30/60 Hz gameplay tick and may frame-limit via vsync/`Present` interval. Unknown whether game time follows wall-clock (variable dt) or a fixed tick.
   - Experiment A: scale `QueryPerformanceCounter`/`timeGetTime` and `Present` interval; observe whether animation speed and draws/frame scale.
   - If variable dt: 120 fps just works once the CPU budget allows.
   - If fixed 60 Hz tick: either (a) run sim at 60 and **interpolate render state** (needs hooking the transform/camera path — substantial RE), or (b) accept 60 sim/120 present with duplicated frames. Decide after the experiment; do not promise true 120 sim before it.

Frame budget at 120 fps = 8.33 ms: target ≤4.5 ms guest CPU, ≤2.5 ms HLE+GL, ≤1.3 ms slack. Wasm is typically 1.3–2x slower than native; native currently does ~5.5 ms/frame of everything at 180 fps, so **expect ~90–120 fps unless we optimise** (Phase 5).

## 4. Phases (do in order; each ends with a screenshot/recording and a metric)

### Phase 0 — Measure and instrument (0.5–1 day)
- Per-frame timers: guest, HLE, serialisation/GL; histogram of frame time; draws/frame, state changes, uploads/frame.
- Dump the game's timing sources (QPC, timeGetTime, Present interval, D3DPRESENT params) -> answer the sim-rate question (Experiment A).
- Record a deterministic input script + golden frame hashes.
- **Exit:** a table of where 8.33 ms would go, and the sim-rate answer.

### Phase 1 — Make it playable natively (days; the real blockers)
1. **Find why the UI doesn't show**: log game state machine; check whether it is waiting on Bink (`BinkOpen` fails ×12). Easiest fix: HLE Bink so every movie "opens" and finishes instantly (`BinkWait`/`BinkDoFrame` report done). Re-run with scripted keys.
2. **Black car body**: check env-map/cube-map sampler binding, sRGB reads, `D3DFMT` mapping, missing render-target/texture format fallbacks in `renderer.js`; diff against a captured D3D draw's state.
3. **Input**: keyboard (done), mouse, Gamepad API -> XInput (analog sticks/triggers) — required for driving feel.
4. **Audio**: identify the audio API the game imports; implement HLE into a ring buffer feeding an AudioWorklet (stub silence first so the game doesn't stall).
5. **Saves/config**: redirect writes to OPFS.
- **Exit:** menu navigable, a race starts and finishes, car textured, silent or with audio.

### Phase 2 — Decouple platform layer (days)
- Define `platform.h` (file, time, thread/yield, GL command sink, audio sink, input source); native and wasm implement it.
- Replace WebSocket serialisation with a direct in-process command sink (native keeps WebSocket as debug view).
- Pre-translate all D3D9 shaders (909 seen so far) ahead of time to GLSL ES 3.00 keyed by bytecode hash; ship as a data file; use `KHR_parallel_shader_compile` and warm the cache before the first frame to avoid hitches. (Alternative: SPIRV-Cross in wasm; offline is cheaper at runtime.)
- Cooperative scheduler as the only thread model (drop pthreads in the wasm path).

### Phase 3 — First wasm build (1–2 weeks; the main risk)
- Boot state: no Unicorn in the browser. Ship the **OEP snapshot** (`re/dump/blur_oep.bin` + register/TEB/thread state) and restore it; CPUID table must stay identical (packer gates).
- Build with Emscripten 6.0.12 (installed): `-mtail-call -O2 -sMAXIMUM_MEMORY=4GB -sALLOW_MEMORY_GROWTH` or fixed memory; guest at address 0 of linear memory.
- **Module size/compile time**: do not compile all 373k functions. Use executed-block coverage (`blocks.txt`, `learned*.txt`, plus new gameplay traces) to build a **hot set**; measure size and Liftoff/TurboFan time on this machine. Target: < ~60 MB wasm, usable first frame < 10 s, code-cached reload < 3 s.
- **Cold-code fallback**: when execution reaches an un-compiled target, call a small x86 interpreter compiled into the wasm (already have the decoder/lifter knowledge; can reuse the oracle semantics) so coverage gaps are slow, not fatal. This replaces the current "learn loop + rebuild" for the browser path.
- Run the module in a **Worker**; main thread handles DOM/audio/gamepad. `OffscreenCanvas` WebGL2 in the Worker.
- File access: user picks the Blur folder (File System Access API / drag-drop) -> copy to OPFS once -> sync reads in the Worker.
- **Exit:** same front-end scene in-browser, no native process, reaching ≥60 fps.

### Phase 4 — Gameplay completeness (weeks)
- Bink movies: transcode offline (ffmpeg has Bink decoders locally) to WebM/H.264 + WebCodecs playback, or skip with option.
- Streaming: 1.2 GB paks via OPFS; no network fetch of game data.
- Audio quality/latency tuning; pause/focus handling; fullscreen; resolution scaling.
- Coverage: run full race(s) with replays, feed new targets into the hot set, bisect any divergences with the oracle.

### Phase 5 — Performance to 120 fps (iterative, metric-driven)
Guest CPU:
- Replace `rt_dispatch` with **direct tail calls for statically known call targets** (keep table dispatch only for indirect/returns).
- Lazy flags and dead-flag elimination in the lifter; keep guest registers in locals across a function; avoid per-instruction budget bookkeeping (check only at back-edges/entries).
- Hot/cold split with `-O2/-O3` for hot functions, `-Oz`/interpreter for cold; consider PGO using recorded traces; run `wasm-opt`.
- Cache-friendly memory layout is mostly fixed by guest, so focus on instruction count.
GL/render:
- Eliminate redundant state sets, cache VAOs/programs/uniform locations, use uniform buffers for constant ranges, orphan/ring-buffer dynamic VBs, texture upload batching, avoid any `readPixels`/sync queries.
- Instanced/multi-draw where the game permits; reduce render-target switches.
- If GL call cost dominates (measure: ≥45k draws/s at 120 fps), write a WebGPU backend with render bundles.
Pacing:
- Present tied to rAF, `desynchronized`/low-latency canvas, `powerPreference: high-performance`; frame-time graph overlay; avoid GC in the JS hot path (typed-array command ring, no per-draw allocation).
- Sim-rate strategy from Phase 0 (variable dt vs fixed tick/interpolation).
- **Exit:** sustained ≥110 fps (p99 frame < 12 ms) in a race on this machine; report honestly if the sim is capped lower.

### Phase 6 — Multiplayer (after single-player is solid)
- Winsock HLE -> WebRTC data channels (+ small lobby/signalling server); LAN-style discovery replaced by lobby codes.
- Needs netcode RE (the game already makes `WSAStartup`/`socket` calls); start with packet capture natively.

## 5. Risks and mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Wasm module too big/slow to compile | High | Hot-set build + interpreter fallback + code cache; measure early (start of Phase 3). |
| Sim locked to fixed tick | Medium | Experiment A in Phase 0; interpolation hook or 60 sim / 120 present. |
| GL overhead caps FPS | Medium | State dedup first; WebGPU backend as escalation. |
| Wasm 4 GB/2 GB limits (guest + host) | Low-Med | Guest ≤2 GB at address 0; measure real committed memory in a race. |
| Anti-tamper/packer behaviour | Low (solved to OEP) | Keep CPUID table fixed; snapshot approach avoids re-running packer. |
| Rebuild fragility of the 500 MB generated C | Known | Hot-set shrink makes the wasm path much smaller; keep the full native build as the reference. |

## Findings log
- F1 (2026-10-16): With `Present` non-blocking and no browser attached, the 3D front-end scene runs at a steady **62 fps / 16.6 ms** per frame; the 5-draw loading screen runs at 200–600 fps. So the ~60 fps cap is **game-internal**, not from the browser/vsync. (The earlier "180 fps" figure was dominated by the loading screen.)
- F2: Game requests `PresentationInterval = ONE` (vsync=1) at 1280x720 fullscreen. Reporting 120/240 Hz via `GetAdapterDisplayMode`/`EnumAdapterModes` (`BLUR_REFRESH`) does **not** change the cap.
- F3: Main thread paces with a Sleep wrapper at 0x4e7f00 called from 0x6cb983 (computes remaining time to a deadline from QPC, Sleep(3..14 ms)). Skipping that Sleep (`BLUR_NOLIMIT`) still gives 62 fps -> there is a second mechanism (likely a fixed-step scheduler/time-scale var at 0x115458c = 100.0). Many code sites reference constant 1/60 (e.g. 0x41adb0, 0x42272a, 0x529058) so the sim uses a baked-in 60 Hz dt widely.
- Implication for 120: a naive uncap will probably speed up the simulation. The plan's options (render interpolation, or 60 sim / 120 present) remain; true 120 Hz simulation would require patching dt constants, which is risky for physics. Decision deferred until the limiter is located.
- Display (M4 Max ProMotion) and CPU are not the limit; per-frame CPU is ~ (1/180 s) at most when uncapped.

- F4 (2026-10-16, wasm size spike): `emcc 6.0.12 -O1 -mtail-call` compiles generated parts fine (musttail OK). One part (`part_00020`, 5.3 MB C): native .o 1.9 MB vs wasm .o 2.1 MB (~1.1x). Extrapolated full set ≈ 260 MB wasm — far too big (Chrome compile 30–60 s+ and the compiled code is 5–7x larger). **Hot-set + interpreter fallback (Phase 3) is mandatory**; first step is runtime function-coverage tracing over a real session (menu + race) to size the hot set.

- F10 (2026-10-16): Added `port/recomp/sse_oracle.py`: one lifted function per SSE/SSE2 instruction form (577 forms: packed/scalar float, int, shuffles, converts, loads/stores, compare+flags) differentially tested against Unicorn (`sse_work/oracle_sse`). Result: **all packed float ops were already correct**; real bugs found+fixed in `lift.py`: `pshuflw/pshufhw` (dropped the untouched half), unsupported `pmuludq`, `cvtpd2dq/cvttpd2dq`, `movntps/movntdq/movntpd` (now plain stores). Final: 577/577 forms, 172,800 trials, 0 mismatches. These fixes take effect on the next full regen (batched; not yet regenerated). => the UI's w=0 constants are **not** an SSE-lane bug; most likely the UI is intentionally faded/hidden until the front-end leaves its movie/attract state (F5–F9).

- F11 (2026-10-16): Guest heap was only 496 MB and the game exhausted it after ~100 s ("guest heap exhausted") -> enlarged to 896 MB (`HEAP_SIZE` 0x38000000) and moved the VirtualAlloc area to 0x58000000. 270 s headless run: no exhaustion, stable ~67 fps, 24k frames. (wasm note: guest addresses stay < 2 GB.)
- F12: XInput pad 0 is now "connected" and keyboard-driven (`hle2.c` `h_XInputGetState`: Enter = Start+A, Space = A, Esc/Backspace = B, arrows = dpad, WASD = left stick; Tab = left shoulder) because the game polls XInput (42k calls/run) and its menus expect a pad. Draws/frame changed 362 -> 373..382 after Enter, i.e. the game reacts (state advances) but still draws nothing visible.
- F13 (**root cause of the missing UI, narrowed**): the UI atlas textures (font 512x1024 DXT1 #1383/#1384, UI atlas 512x512 DXT5 #1382, etc.) are created at frame 1 by the texture-creation path (Lock/Unlock wrapper at 0x5c0b00) and are **all-zero in guest memory at every later draw** (`BLUR_UITEX=1` live check = 0 %); `BLUR_TEXSTAT=1` shows ~140 DXT5/DXT1 textures uploaded all-zero. A write watch (`BLUR_WATCHW=lo-hi`, mprotect + SIGSEGV, filters host-side writers) shows **no guest code ever writes into those pages after creation** (40 s). So the UI texture data is never loaded: the loader that should populate them (boot layer / streaming) is not delivering. Earlier "c23/c24 w=0" (F6) is a consequence/red herring: those PS constants (c21–c25) are post-process tap offsets in other passes.
- F14: Only 11 files are opened (root.pak, root_streaming.pak 5 reads only, shaders-speed.pak, gamedata.sig/pak, boot.pak 557 reads, lut_rampak.pak, 4 showroom level files); all succeed. `gamedata_boot.pak`/`boot_rampak.pak` are NOT opened because `Amax.BootLayer.BootRamPakEnable` defaults to 0 (ctor pushes 0; flag byte at 0x1226f94), while `BootPakEnable` defaults to 1 (boot.pak). Thread dump (`BLUR_THREADS=1`): only the main thread runs; ~13 worker/job threads are blocked in WaitForSingleObject(-1) on events (ret 0x51814f / 0x5180bb / 0x511d34) and two Sleep(1) pollers; `Amax.BootLayer.MovieStallBodgeValue` suggests the boot layer is gated on the boot movie.
- F15: Next UI hypotheses, in order: (1) the front-end UI streaming request is gated on the boot-movie finishing -> implement a real/complete Bink path (right frame count/dims/audio) or skip; (2) a missing event/semaphore wake-up in our Win32 sync HLE leaves the streaming worker threads blocked (examine which event the main thread SetEvent's vs what workers wait on; check auto/manual reset, ReleaseSemaphore counts, WaitForMultipleObjects); (3) try `BootRamPakEnable=1` path (needs `boot_rampak.pak` which does not exist -> likely generated by the game).

- F17 (2026-10-16, **hot-set sizing**): `BLUR_COVER=<file>` records every recompiled function entered. A 100 s showroom session (front-end scene, scripted key taps) enters **45,964 of 373,530 functions (12 %)**; that is **14.6 MB of the 144.8 MB native code (10 %)** (`port/recomp/cover_showroom.txt`). Extrapolated wasm hot module for the showroom ≈ 15–20 MB; a full race will add more (to be measured once a race can be started). This confirms the hot-set + fallback design is feasible: Liftoff compiles tens of MB/s, so a ~20–40 MB module compiles in seconds.

- F18 (2026-10-16, **wasm feasibility spike — passed**): new tools `port/recomp/hot_extract.py` (extract hot subset from generated C, closes over direct references, writes `gen_hot/`) and `BLUR_COVER`. From the showroom coverage: 45,964 entered functions -> 92,184 after closure (107.7 MB of C). `emcc -O1 -mtail-call` compiles all 27 parts in **11.6 s wall** (14 jobs); linked with stub runtime the module is **40.4 MB wasm / 5.9 MB gzip**; V8 (node 22) eager `WebAssembly.compile` = **180 ms** (Liftoff baseline; TurboFan tiers up in the background). A 2.5 GB and a 4 GB `WebAssembly.Memory` allocate fine in V8. Conclusion: compile time is NOT a blocker; the hot set is small enough to ship as a single module.
- F19 (Phase 3 design, decided): (a) guest address == wasm linear-memory address (`G` becomes constant 0; plain wasm loads/stores); guest user space is < 2 GB (msvcr90 at 0x78520000, TEB/PEB 0x7ffd....), so reserve the low 2 GB for the guest and link the module's static data/stack/malloc heap *above* it (`--global-base` >= 0x80000000, max memory 4 GB). (b) Boot: no Unicorn — start from an **OEP snapshot** (`re/dump/blur_oep.bin` + sparse dump of other mapped regions + serialized `Ctx` incl. stub order, handles, module table, TEB/TLS, thread 0 regs) produced by a new native `BLUR_SNAPSHOT=` switch; wasm restores it. (c) Single-threaded cooperative scheduler: each guest thread is a `Cpu`+guest stack; `rt_yield` returns out of the tail-call chain to a scheduler loop (no pthreads, no SharedArrayBuffer). (d) Run loop returns to JS at `Present` (and when all threads are blocked) -> `requestAnimationFrame` drives the next slice; no Asyncify. (e) Shaders: translate D3D9 bytecode -> GLSL ES 3.00 **offline** from `shaders-speed.pak` into a hash-keyed cache (removes vkd3d-shader/SPIRV-Cross from the wasm). (f) Files: guest `ReadFile` -> OPFS sync access handles in the Worker. (g) Cold code (not in hot set): x86 interpreter fallback; until it exists, log + stop.

## Decisions
- D2 (2026-10-17, user, **supersedes the delivery target of D1**): The end goal is **to be able to play Blur in a race at a solid 60 fps in fullscreen**. The delivery vehicle is open: browser (WebGL2 / wasm), native window (native harness + native renderer), or anything else that works. Priority is the playable outcome, not the browser. Consequences: (1) the measured blocker is guest CPU time while driving (17-20 fps host-bound, F130), so the first lever is faster guest execution (build flags/PGO, cheaper dispatch, running guest worker threads in parallel on host threads), and a native window with a native renderer is allowed if it removes the WebSocket/browser cost; (2) fullscreen must work (real fullscreen / pointer lock / resolution scaling) and be verified; (3) correctness bugs seen in play stay in scope (mirror, Retry, reverse-gear key sticking, heap exhaustion).
- D1 (2026-10-16, user): The game's baked-in 60 Hz simulation stays. **Target is a rock-solid 60 fps** (p99 frame ≤ 16.7 ms, no hitches) at maximum quality settings in the browser; 120 Hz sim/interpolation is dropped from scope (optional later experiment only). Phase 5 therefore optimises for frame-time consistency, load/compile stalls, and headroom (so 60 holds on lesser hardware too), and for graphics quality (max resolution/MSAA/anisotropy, correct materials) rather than raw fps.

- F5 (UI fork, 2026-10-16): the game is in the **showroom front-end** (loads `levels\showroom\*`, `IsFrontEndLoading`/`SetFrontEndLoaded`, `PressStartActionIn`); the 3D scene is the menu background. The UI IS drawn every frame (about 7 draws at the end of the frame: 2 quads from a 512x512 DXT5 atlas, 8+4 glyph quads from a 512x1024 DXT1 font atlas, a full-screen 16x16 overlay), through VS 344 B / PS 596 B & 680 B into an offscreen 1280x720 texture RT, which is composited over the scene (vs#39/ps#2748, blend ONE/INVSRCALPHA). Positions are sane (bottom-left text, safe-frame coordinates).
- F6: the UI pixel shaders (CTAB: `g_LightPos c21, g_LightDir c22, g_LightColourFrom c23, g_LightColourTo c24, g_LightFallOff c25`) output `alpha = tex.a * vertex.a * lerp(c23,c24,t).w`. At UI draw time c23 = (0.02,0.02,0,0) and c24 = (274.6,93.4,44.1,0): **w = 0, so the UI is fully transparent** (alpha test is on, GREATER 0, so it is discarded). Values come from the game's own parameter blocks in guest memory (set via one generic wrapper at 0x5ba1e6, ~570k SetPixelShaderConstantF calls/run), i.e. the game itself writes w=0 / z=0. Hypotheses still open: (a) a lifted SSE instruction loses z/w lanes when the game builds these vec4s (c24 looks like an orange RGB, which would need alpha), (b) the UI really is faded out until the front-end state advances (input / movie / timeline).
- F7: forcing c23/c24 = white/alpha 1 before each UI draw (`BLUR_UIFORCE=1`) did not make text appear in the browser; renderer readback (`#dbg` page flag, `dbgReadRT`) shows the UI render target stays all-zero most frames and is non-zero only occasionally (one sample 25k px, max 253), so UI output is intermittent/animated — a time series of screenshots across the idle period was not completed (browser session dropped), so this is unconfirmed.
- F8: `BINK_FAKE=1` crashes unless `BINK_SETS=1` (game locks two sets of 4 plane textures and the second set's textures are NULL). With `BINK_SETS=1 BINK_FAKE=1` the run is stable, the camera orbit/showroom view proceeds and draws/frame is 363; 4 fixed-function draws per frame are skipped by the renderer (movie quad path: "fixed-function pipeline not implemented").
- F9: Fixes/tools added: `d3d9_set_const` now forwards constant-table writes to the renderer (the game never uses them in practice); `BLUR_DRAWDUMP=N` (dump all draws of first frame with >=N draws), `BLUR_DRAWCONST=1` (+VS c32–35, PS c21–25, vertex data, scissor/colour-write state), `BLUR_PSLOG=1` (log PS const sets c21–25 with caller/source memory), `BLUR_UIFORCE=1`, `BLUR_STATS` now lists 120 APIs, renderer `#dbg` flag. NOTE: the dump's `rt=` field is unreliable (UI actually draws to texture RT, not the backbuffer). Browser must connect before the game starts; a reconnecting page misses resource creation (all draws skipped) — use one shot.js session per run.
- Next steps for UI: (1) test hypothesis (a) by finding the writer of the parameter blocks (e.g. memory watch via a page-protect/instrumented store, or oracle-diff the SSE ops used there); (2) record a long screenshot series in one browser session to see whether the text blinks; (3) implement a real Bink path (or the fixed-function quad) so the front-end can leave its movie states; (4) also check whether the same z/w-loss explains the black car (paint colours).

## Phase 4 (2026-10-23): browser-native direction, learned from cricket07.dhaiwat.com and nfsmwonline.com (F154)
Findings: Cricket 07 = statically recompiled exe -> wasm + WebGPU + OPFS content-hash download + AudioWorklet reading wasm memory + COOP/COEP isolation; NFSMW = custom Rust engine, WebGPU (render bundles, indirect draws, compute), Cache API keyed by content hash, converted asset formats. Notes in /tmp/claude-501/sites (not kept).
Tracks (each a spike first, with a measured go/no-go):
- **A cache + LAN serving (low risk):** hash texture/shader/buffer uploads host-side, page keeps them in IndexedDB/OPFS keyed by hash, host sends hash refs for known content; optional `BLUR_BIND=0.0.0.0` to serve other LAN browsers; secure-context handling (WebGPU/OPFS/SAB need https or localhost; launcher passes `--unsafely-treat-insecure-origin-as-secure=<origin>` for LAN origins).
- **B WebGPU renderer:** goal is cutting the page's per-draw JS cost (F146/F149) via render bundles/indirect draws. Open problem: D3D9 bytecode -> SPIR-V (vkd3d) -> GLSL (SPIRV-Cross) today; WebGPU needs WGSL (naga/tint). Spike = one captured frame rendered through WebGPU, compare JS ms/frame against WebGL2.
- **C full wasm:** guest addr == wasm addr, hot-set module (see Phase 3 design). Risk: race fps was guest-CPU-bound on native (17-20 fps pre-BLUR_PAR); wasm is typically slower than native. Spike must measure lifted-code throughput in wasm (threads + SAB) against native before any full port.
Storage lifetime (answer to the user): OPFS/Cache API are per-origin; lost on clear-site-data, incognito close, eviction under pressure unless `navigator.storage.persist()` is granted, or a different origin (host/port). Hash-named files mean only changed files re-download.

- F156 **Track A: content-hash cache + optional LAN serving (2026-10-23)**. *Measured first* (`BLUR_HCSTAT=1`, per-message-type raw bytes; headless Chromium, boot -> title -> attract/career movies): the stream is 1.1 GB in the first 45 s and ~9.4 GB over a 200 s session that includes the career intro Bink movie.
