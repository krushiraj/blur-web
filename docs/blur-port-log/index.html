Putting a 2010 PC racer in a browser tab

Blur's x86 executable was statically recompiled to C, linked against a hand-written Win32/Direct3D 9 host, and its draw commands are streamed to a WebGL2 or WebGPU page. This is the log of what we planned, what broke, how we found out why, and what we decided along the way.

Machine Apple M4 Max, 128 GB Target solid 60 fps race, fullscreen Also builds for Windows x64, Linux x64 and arm64 Sources PLAN_120FPS.md (F1–F159), agent reports, session history

0The short version

The project started as "can Blur run in a browser at up to 120 fps?" It ended up as a native runtime with a browser front end, because the measurements said so at each step. The 120 fps goal was dropped on day two (the game's simulation is baked at 60 Hz) and the target became a rock-solid 60 fps in a race.

What actually mattered
  1. Static recompilation beat emulation. The Unicorn emulator never got past the loading screen at usable speed. Lifting the code to C gave ~180 command-generation frames per second on its own.
  2. Most "rendering bugs" were host-API bugs. The empty UI, the washed-out scene, and the heap crash were all a stubbed or wrong Windows/D3D9 call, not a renderer or CPU-translation bug.
  3. Race speed was CPU-scheduling bound, not browser bound. The measured fix was one host thread per guest thread. Everything in the renderer helped at the margin; the thread model changed the order of magnitude.
  4. Opt-in browser backends need regression checks of their own. Two of the nastiest bugs in the last days were self-inflicted: a message-type collision in the new cache protocol and an invalid WebGPU sampler that silently threw away whole frames.

1Premise and ground rules

Blur (Bizarre Creations, Activision, 2010) is a Direct3D 9 game with up to 20-player online and LAN racing. The official servers are gone and the game depends on the defunct Games for Windows Live. The goal was to learn how far static recompilation can take a game this size, and to get it playable on the author's own machines.

Ground rules we kept
  • Personal learning only. The game files are the user's own copy and stay on their machines. The zips built for the home setup contain that copy and are not for distribution.
  • No game bytes in anything public. The original plan said ship the runtime and the translator, never the lifted C or the assets. Nothing was published.
  • Refused out-of-scope help. When pointed at two browser game sites to learn from, we studied their client architecture only. We did not download or run their unlicensed game copies.
  • Working habits. Never create accounts or type credentials on websites; no commits or pushes unless asked; yarn, not npm; do not touch the user's own running game instances while testing (we used separate ports and killed only our own processes).

The original research note (BLUR_WEB_PORT_PLAN.md) also records the legal caution that applies to any public release: reverse-engineering for interoperability has precedent in US case law, but contract terms and DRM are separate, so a lawyer should read it before anything is shared.

Engineering method written down on day one

  1. Metrics before features. Per-frame time split (guest code, host APIs, command encode, GL) first; every later decision follows numbers.
  2. The native build is the reference harness. Fix game and rendering bugs natively (fast rebuilds, real debuggers, differential oracle), then port. Never debug game logic and the wasm port at the same time.
  3. Vertical slice early. Menu → race → finish on the slow simple path, then optimise measured hot spots.
  4. Platform-layer boundary. Win32, D3D9, audio, input and file HLE ("high-level emulation" = our own implementation of the Windows calls) sit behind a small interface.
  5. Regression safety. Deterministic input replay, golden frame hashes, and the instruction-level oracle on every recompiler change.

Four ideas that carry the design

1. The emulator only boots; recompiled code runs the game.
Blur.exe is protected by a packer (the .8thSin section). Its stub decrypts the image and uses "call gates" that derive jump targets from the CPU's CPUID and rewrite return addresses. Unicorn runs it to the original entry point; from there a snapshot of memory is taken and the recompiled code takes over. Because the packer reads CPUID, the emulator version must be identical everywhere (we later hit this on Linux, section 9).
2. Every call, return and indirect jump is a tail call through a dispatcher.
The guest stack alone defines control flow, which is what the packer's return-address tricks need. Lifted functions end in MUSTTAIL calls to rt_dispatch, which looks the target up in a table. Flags travel in the CPU struct; host APIs are stubs the dispatcher recognises by address.
3. Guest memory is one flat mapping at a fixed address.
The host maps the guest's 4 GB at 0x7000000000. Compiling the lifted code with that base as a constant removed a reload of the base pointer after every guest store (section 7).
4. The renderer is a remote.
D3D9 calls become a compact binary message stream (create texture, set state, draw, present). The page replays it. That boundary is what later let us swap WebGL2 for WebGPU, add a content-hash cache, and compare renderers on recorded frames.

Each entry is: what we saw, what we tried, the real cause, and the fix. Longer stories first; the rest are in the table at the end.

6.1 The empty UI: 140 textures full of zeros

Symptom
The 3D menu scene rendered but no text, icons or buttons. The UI atlases (font 512×1024 DXT1, UI atlas 512×512 DXT5, about 140 textures) were all zeros at every draw.
Wrong turns
Pixel shader constants c21–c25 had alpha 0 (a consequence, not a cause). An SSE lane bug in the lifter (oracle said no). A broken Bink movie gating the boot layer (faking it did not help). A missing event waking a worker thread (job system was alive). Raising crypto handle limits. A recompiler fault: the pure Unicorn emulator showed the same zero statistics, which cleared the recompiler.
Clues that mattered
A write watch on the font atlas saw no write for 150 s. The pak files and their table of contents decoded fine and the UI bank requests were read in full. A runtime-created icon atlas was non-zero, so banks loaded dynamically; only some textures stayed empty.
Root cause
IDirect3DResource9::GetType was a stub returning 0. The game's texture helper (0x5aa710) switched on the resource type, got "unknown" and computed row size 0, so the bank uploader copied zero bytes into every bank texture.
Fix
Return the real type from GetType. A related earlier fix (parse_ctab read the constant table at the wrong offset, so every ID3DXConstantTable held garbage) and input validation on CreateTexture followed. Both were independently found by different agents.

Lesson

A stub that returns a plausible value (0) is more dangerous than one that fails loudly. We added BLUR_STRICT=1 (log "succeeded where Windows would fail") and an argument recorder (BLUR_ARGREC) to audit every stub, and found a handful more: caps fields the game reads, getters that did not fill their outputs.

6.2 The crash at frame ~7,400: a zero-sized texture

Symptom
Every run died around frame 7,200–7,600 at 0x5ab7c4: call [vtable+8] (a COM Release) on an object whose vtable word was garbage that changed per run. It appeared natively, in the emulator and in wasm, so it was not a recompiler problem.
Investigation
A per-thread ring of the last 256 function entries, heap canaries behind every allocation, a heap-poisoning mode, and a "strict" mode. Different agents found the same pattern: the bad pointer always had [esp]=005ab7c6, always at the loading→showroom transition.
Root cause
The game calls CreateTexture(Width=0, Height=0, Levels=7, DXT1). We returned success with a 56-byte placeholder. The game then wrote real mip data (DXT blocks) into it, smashing the neighbouring object's vtable.
Fix
Validate creation parameters and return D3DERR_INVALIDCALL with a null out pointer, as real D3D9 does. Same guards for volume, cube, buffer and render-target creation.
Lesson

A "flaky crash with random garbage" that survives three execution engines is a host-side memory bug. The fastest route was making failures reproducible and loud (ring buffer, canaries) rather than reading generated code.

6.3 The washed-out scene: same symptom, two different causes

Blur does automatic exposure. Every frame it renders the scene to a small target, reduces it to a 1×1 float texture ("adapted luminance"), and reads that texel back on the CPU with GetRenderTargetData to set exposure constants for the next frame. The renderer lives in the browser, so the readback has to travel: host → page (read the texel) → page → host (send the value) → guest memory.

Round 1: October 16, the stub

Symptom
The whole scene saturated to pink-white. No city, no car body.
Root cause
GetRenderTargetData was a stub, so the CPU read luminance 0 and the game computed maximum exposure: the pixel shader constant c31 became (100, 0.01, …).
Fix
Message 81 asks the page to read texel (0,0); the page answers with input type 10; the host writes the float into the destination surface. The page reads it asynchronously with a pixel-pack buffer and a fence, because a synchronous readPixels per frame stalled the GPU (about 30% of page time in a race).

Round 2: October 23, the collision

Symptom
The user reported "the gamma issue is back", on both WebGL2 and WebGPU. The title screen was pink again, and this time the 3D city and car were missing too.
First wrong guess (ours)
We assumed the new WebGPU path lacked a gamma ramp and implemented one. The WebGL2 page showed the same pink, which killed that theory: the bug was common to both renderers. The gamma-ramp code is harmless but was not the cause.
Method
(1) The old pre-merge binary on the same page rendered correctly, so the page was fine and the host binary was at fault. (2) Disabling the hash cache did not help. (3) Both binaries sent the same message types and counts. (4) We recorded each stream and diffed the last frame message by message: every draw was identical, texture ids differed only in numbering, but two pixel-shader constants differed: c31 = (100, 0.01, …) in the bad build and (1, 1, …) in the good one. That is exactly the "luminance read as 0" signature of round 1.
Root cause
See the next entry: the new cache protocol swallowed the readback answer.
Lesson

"Known issue in both renderers" is a smell. If two independent implementations agree on a wrong picture, the bug is upstream of both. And a regression is best found by diffing data (constants per draw) between a good and a bad build, not by looking at pictures.

6.4 The new cache protocol ate the exposure answer (F159)

Cause
Page → host messages are small binary frames whose first 32-bit word is a type: 1 key down, 2 key up, … 10 readback answer. The new hash cache needed two extra page → host messages (an "announce" of known hashes, and a "stored" acknowledgement) and used the numbers 10 and 12. The host's receive loop treated every frame starting with 10 or 12 as a cache message and never queued it as input.
Why it escaped
Everything else worked. Keyboard, mouse and the cache itself were fine; the one affected message type is only consumed by the exposure code. Our checks looked at fps, draws and "does the picture exist", not the colour.
Fix
Cache messages now use their own codes 0x48430A and 0x48430C ("HC" + 0x0A / 0x0C) in hcache.js, net.c and gfx.c. Verified by screenshot (night city and car back) and by a hook that logs the type-10 answers.

Lesson

When a protocol grows a second use, give it its own namespace. A sentinel-style range (here a 24-bit "magic" prefix) is cheap insurance. A wire-protocol checklist item for any new message: "does its type code collide with an existing one, in either direction?"

6.5 The race that never started: undefined behaviour in generated C

Symptom
At the start of a race the native process stopped advancing: 0 fps, half-drawn frame, watchdog "no scheduling progress", last thread stuck at 0x4cb1dd. The log was full of "Potentially bad data" lines, which looked suspicious but are normal developer output.
Root cause
The lifted code reads floats with *(float*) and stores 8 bytes with *(uint64_t*), but the build had no -fno-strict-aliasing. In the unguarded insertion sort f_004d1310 the game does movq [esp+0x40], xmm3 then comiss xmm2, [esp+0x44]. Clang assumed the 64-bit store cannot change a float and hoisted the load out of the loop (visible in the disassembly: one ldr s1 before the loop, none inside), so the comparison never changed.
Found by
Two agents independently, one by bisecting toggles and one by reading the machine code of the stuck function.
Fix
Compile with -fno-strict-aliasing. The wasm build was only spared because race code ran in the interpreter. Rebuilt objects also pick up this flag in the fast build recipe.
Lesson

A loop that never terminates in correct-looking lifted code is a compiler assumption problem before it is a logic problem. Look at the generated machine code for the loop.

6.6 Black frames in WebGPU: one invalid sampler drops the whole frame

Symptom
From a screen recording: about a second of pure black when a taxi swerved close to the player's car, with the HUD graph still running. Other users of a WebGPU page would see "frames missing" in cutscenes or after impacts.
Method
A scripted race drive on #gpu=1 with console capture. The log showed 66 × "[Invalid Sampler] is invalid → [Invalid BindGroup] → [Invalid CommandBuffer]" and the WebGPU validation message: minFilter/magFilter/mipmapFilter must all be linear when maxAnisotropy > 1.
Root cause
The game requests anisotropic filtering with one filter set to point sampling or no mip filter. WebGL2 tolerated that; WebGPU makes the sampler invalid, which invalidates every bind group that uses it, which invalidates the whole command buffer for the frame. Chrome drops the submit and the canvas shows black.
Fix
When anisotropy > 1, force min, mag and mipmap filters to linear. Re-run: 137 warnings before, 1 afterwards (the harmless "audio needs a click" notice), zero Invalid messages.
Lesson

WebGPU's validation is all-or-nothing per submit. Add error scopes or run with the console open during testing, and treat any "Invalid …" line as a dropped frame, not a warning.

7The road to 60 fps

The user's goal changed on October 16–17: "a solid 60 fps in a race in fullscreen, whatever it takes". The 120 fps idea was dropped because Blur's simulation is built around a 60 Hz step (many code paths reference 1/60), so speeding up the presentation would speed up the game.

Race frame rate through the project
Not a benchmark suite: each bar is the number the log or a user screenshot reported at that point, in the state described. "Heavy scene" means 3,000+ draws per frame.

Where the game stands now: evidence from a screen recording

On the last day the user recorded a WebGPU race on the Mac. Frame-time HUD readings from that video line up with draw counts: the heavier the scene, the lower the fps. The recording itself (3600×2260 at 120 Hz) costs GPU time, so real numbers may be a little better.

What this does and does not show

Pipelines were not compiling (0 pending, 0 skipped), so it is not shader compilation. The HUD measures time between the game's frames arriving at the page, so a slow frame means either the host produced it late or the page was busy. The next measurement is BLUR_PROF=120 on the host together with the HUD's new "page JS per frame" line.

Finding the limiter

  1. The page was not the bottleneck. In the user's real Chrome the HUD showed page JavaScript at 12–16 ms/frame, but the host's own fps log matched the page fps. With no viewer at all (BLUR_NOWAIT) and the accelerator held, the host alone ran 17–30 fps.
  2. The host was half asleep. The main thread spent about half of each 60 ms frame idle in the cooperative scheduler. A profile (BLUR_PROF) showed three heavy guest threads (≈16, 15 and 12 ms) executed one after the other by a single host thread, with 6,000 context switches per frame.
  3. The fix was one host thread per guest thread (BLUR_PAR=1). A global lock is held only inside API handlers (the HLE stays single-threaded by construction); blocked threads park on a per-thread condition variable and are woken after each API call re-evaluates who can run. The lifter already emitted sequentially-consistent atomics for lock/xchg.

8Multiplayer

What the game does on the network

Reverse engineering (port/work/net-re/NETCODE.md) found that Blur's networking is the Demonware "bd" SDK plus Bizarre's own session layer:

  • All gameplay traffic is non-blocking UDP polled once per frame through plain socket/bind/sendto/recvfrom. TCP/OpenSSL/curl exist only for the dead online services.
  • Datagrams are at most 1,288 bytes. Per peer: NAT traversal, a DTLS-like handshake (HMAC + Diffie-Hellman keyed by a security id), then an own message layer (10-byte header, ≤1 KB fragments, sequence numbers, reliable/unreliable channels).
  • Not lockstep: state is replicated. Each car is a 25-byte record (24 bytes of bit-packed rigid-body state plus a feedback byte), sent about every 100 ms; 25 ordered race events (hits, spawns, boosts, abilities) ride in one message type.
  • LAN mode exists and needs no backend. Discovery is a UDP broadcast on port 50001 (24-byte query, 160-byte reply, 2 s window, 10 hosts max). Up to 20 players.

Track A: content-hash cache

Measure first

Per-message-type raw byte counts from the host (BLUR_HCSTAT=1): the page receives 1.1 GB in the first 45 s and about 9.4 GB over 200 s if the career intro movie plays. Texture uploads are 85–97% of all bytes. Vertex/index buffers are 0.3%, shaders 0.04 MB (already offline-cached), state and draw messages about 10%.

Where the first 1.1 GB goes (first 45 s: boot, title, attract movies)
The Bink movie traffic cannot be cached: it is one of a few 640×360 or 1280×720 textures re-uploaded with new pixels every frame (about 120 MB/s). Over a 200 s session that includes the career intro movie the total reaches about 9.4 GB.

Design

  • The host rewrites each finished batch right before sending; message producers are untouched.
  • Only uploads of at least 2 KB from objects that have uploaded at most twice are hashed. That keeps video frames and dynamic buffers out.
  • Hash: a 64-bit multiply-fold (wyhash-style, two lanes, about 8–10 GB/s).
  • The page keeps payloads in IndexedDB (192 MB memory layer in front, default cap 1,536 MB with LRU eviction at startup), and announces its hashes at connect; the host waits up to 3 s for that.
  • A hash counts as known only after the IndexedDB write commits (ack message), so the host never refers to something the page might have lost.
  • IndexedDB writes are throttled (slices ≤3 MB, only while the last 12 presents average ≤18 ms, pending queue ≤160 MB) because the first version dipped to 41–44 fps on first visit.

Results

Same run, title screen idle, ~43 s after start
Visit 2: 5,228 refs (236 MB of texture data not sent), 0 misses. A verification run compared 5,084 uploads (244 MB) byte for byte: 0 mismatches. fps stayed at 60.

Cache lifetime (answer to "when is the download lost?")

  • OPFS, Cache API and IndexedDB are per origin (host and port). Another port or a LAN address is a different cache.
  • Lost on "clear site data", when a private window closes, and evicted under storage pressure unless navigator.storage.persist() is granted.
  • Hash-named content means only changed content re-downloads. A game update is cheap; a browser reset is not.
  • WebGPU, OPFS and SharedArrayBuffer need a secure context (https or localhost). Another machine on plain http needs Chrome's --unsafely-treat-insecure-origin-as-secure=<origin> flag or https.

Draw-cost benchmark

JS milliseconds per frame, 3,000 indexed draws, headless Chromium 141, M4 Max
Trivial shaders and draws: this measures the API's JavaScript cost, not GPU shading. Real Chrome 157 gave 5.2 vs 0.92 ms (calibrated) and 9.34 vs 1.88 ms (heavy). Render bundles only win when whole chunks repeat byte for byte frame to frame, which D3D9 streams rarely do, so they are optional.

How the renderer maps D3D9 to WebGPU

  • Pipeline cache keyed by (VS, PS, vertex layout, blend incl. separate alpha, colour mask, depth, stencil, cull, topology, target formats, sample count, depth bias). Viewport, scissor, stencil ref and blend constant are dynamic.
  • Async compile, at most 6 in flight. While a draw's pipeline compiles, the frame is held (last complete frame stays on screen, up to 30 frames), then the draw is skipped and counted.
  • Warm list of 431 pipelines (340 from replayed scenes plus 91 from live race-grid exports) plus recipes learned in earlier sessions (IndexedDB). Pipelines took p50 103 ms, p95 329 ms to create serially, which is why this matters.
  • Per-draw constants through a ring buffer with dynamic offsets (about 1.3 KB per draw, 4 MB per frame).
  • Vertex fix-ups: unorm8x4-bgra is absent in this Chrome, so COLOR0/1 swizzle through a pipeline-overridable constant; missing elements point at a zero-stride dummy buffer.
  • sRGB: WebGPU decodes sRGB before filtering (the D3D-correct order); WebGL2 decodes after.
  • A render target sampled in the same pass is illegal in WebGPU: end pass, copy, new pass with loadOp: load.

Validation: replay recorded frames against WebGL2

Three scenes were captured from the host (title 591 draws, career 735 draws, race 2,364 draws over 6 consecutive frames) as raw message streams. The same bytes were rendered by both renderers and compared per pixel: for the race frame, 98.8% of pixels within 8/255. A whole-game wasm build already existed (port/web): wasm module of the hot functions plus the interpreter fallback and the WebGL2 renderer in a Worker. 13Lessons

  1. Build the measuring tools before the features. The frame profiler, stream dump and API recorder produced every important root cause.
  2. The first suspect is almost never right. UI bug: seven hypotheses, six wrong. Gamma bug: we implemented a gamma ramp for a protocol collision.
  3. A stub that returns success is a lie. Prefer a loud failure plus an audit tool (BLUR_STRICT, argument recorder).
  4. Two independent implementations agreeing on a wrong picture means the bug is upstream.
  5. Diff data, not pictures. Constants per draw in a good and a bad build pinpointed a bug no screenshot could.
  6. Verify "it's fast" is real. A frozen scene reports 60 fps. Check that draws per frame vary.
  7. A/B every optimisation against the old binary with the same paced input; reject what does not move the number.
  8. Treat extension protocols as public APIs. Namespace new message types; check collisions in both directions.
  9. With WebGPU, "warning" often means "this frame is gone". Capture the console in every scripted run and fail on "Invalid".
  10. Keep the reference build and the reference screenshot. The one thing that settled the colour bug fast was an older binary that still worked.
  11. Decide by measurement, document the loser. Wasm was a fair fight on paper; the 1.5–1.85× number ended it in an afternoon.

E. Glossary

HLE
High-level emulation: reimplementing an operating-system or library API instead of emulating the hardware under it.
OEP
Original entry point: where the game's real code starts, after a packer has unpacked it.
Lifting
Translating machine code (here x86) to a higher-level language (C) function by function.
Hot set
The functions actually executed in recorded sessions; used to size a wasm module.
Present
The D3D9 call that ends a frame; our page frame timing is measured between these.
WGSL / SPIR-V
WebGPU's shader language and the Vulkan intermediate shader format.
Render bundle
A pre-recorded WebGPU command list that can be replayed cheaply.
OPFS / IndexedDB
Browser file system and database storage, per origin.
